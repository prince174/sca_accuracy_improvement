# Оценки компонентов и фильтрация SBOM

Политика `tp-score-gt-70-v1`: в результирующем списке компонентов остаются
только записи с **TP score > 70**. Ровно 70 исключается. Это оценка корректности
идентичности и присутствия компонента в поставляемом образе, не вероятность
уязвимости или эксплуатации. FP score = 100 − TP score.

Проценты пока являются некалиброванной оценкой модели. Порог — выбранная политика
продукта, не доказанная гарантия качества. Исключение записи не означает,
что отсутствие компонента или неприменимость CVE доказаны.

Метки отчёта: `TP` при score > 70, `FP` при score < 30, `uncertain` от 30 до 70
включительно. Это предположения модели; метка не является эталонной разметкой.
В SBOM не включаются и FP, и uncertain, но оба остаются в полном отчёте.

Оценивается объединение исходных компонентов и идентичностей, обнаруженных в
образе, включая слабые/неразрешённые наблюдения. Записи одной нормализованной
идентичности получают одну оценку; исходные отдельные bom-ref сохраняются.
Компоненты, встречающиеся только в исходниках, служат контекстом и не добавляются
в состав поставки автоматически. `metadata.component` описывает сам продукт:
он сохраняется как субъект документа; его дочерние компоненты фильтруются.

## Проверки кода

Каждый компонент должен получить ровно одну оценку. Неизвестный/повторный ID,
пропущенный ответ, NaN/Infinity, число вне 0–100, строка вместо числа, неизвестная
ссылка на evidence и некорректные поля приводят к ошибке анализа. Частичный ответ
не превращается в частично отфильтрованный успешный SBOM. Модель не может задавать
собственные операции или изменять package identity произвольным текстом.

После проверки код сам применяет порог. Для исключённых компонентов удаляются
узлы/рёбра dependencies, ссылки compositions/annotations и соответствующие affects
встроенных vulnerabilities. Уязвимость, относящаяся только к исключённым записям,
исчезает из производного документа; исходный SBOM сохраняет её. Это структурная
фильтрация, не VEX `not_affected`. Неизвестная структура с оставшейся ссылкой на
исключённый компонент блокирует публикацию, а не сохраняется заведомо сломанной.

Если родитель исключён, а вложенный компонент прошёл порог, вложенный компонент
поднимается на уровень выше. Новые связи зависимостей не выдумываются. Метаданные
политики явно обозначают производный отфильтрованный состав. Подписи, переставшие
соответствовать изменённому документу, удаляются; оригинал остаётся без изменений.

В отчёте сохраняются все оценки, причины, ссылки на evidence, недостающие данные,
факт включения/исключения и журнал очистки связей. Оценки включённых компонентов
также записываются в CycloneDX `properties` с префиксом `sca-accuracy:`.

Эта политика заменяет прежний выбор моделью `apply/defer` в основном модельном
потоке (`with_llm: true`, по умолчанию в API v2). Модель получает каталог порциями
до 40 компонентов и до 96 000 байт JSON на порцию; каждый ответ проверяется
до применения всего результата. Слишком большая одиночная запись завершает
анализ ошибкой, а не теряется. Лимит байт не является точным лимитом токенов.
Артефакт `component-scores.json` и таблица в `report.html` содержат все оценки.
Исторические benchmarks старого режима
сохраняются отдельно; их метрики не описывают новую фильтрацию.

## Проверка через работающий сервис

`golden/evidence/verify_scoring_service.py --live` собирает три контролируемых
образа (Java, npm, две версии npm), передаёт задания HTTP-сервису с моделью,
скачивает отчёты и проверяет соответствие выходных компонентов порогу, полноту
оценок, сохранность оригинала и SHA-256 оценок в evidence-хранилище. Контейнеры
целевых образов не запускаются. Для Java нужен JAR из `golden/build.py`.

```bash
uv run --env-file .env python golden/evidence/verify_scoring_service.py --live
```

Сервис должен иметь настроенный модельный endpoint и ключ; клиент использует
`SCA_API_TOKEN` и `SCA_SERVICE_URL` (по умолчанию `http://127.0.0.1:18087`).
В `out/scoring-service-live/acceptance.json` отдельно записываются проверки
контракта и ошибки состава относительно конструктора образов. Три простых
примера не заменяют оценку качества на размеченных реальных сборках.

Для сравнения на неизменных входах передайте `--baseline out/scoring-service-live-2`
и отдельный `--output`: будут повторно использованы сохранённые image digest и
исходные SBOM, без пересборки. Скрипт проверяет совпадение digest и сохраняет
прошлые FP/FN рядом с новыми. Эталон конструктора не включается в запрос модели.

[Результаты живой проверки 21.09.2026](scoring-acceptance.md), включая найденный
ложный компонент с баллом выше порога и отклонённый валидатором ответ.

## Контекст идентификации

Модель получает выбранные identity-поля исходных metadata Syft, включая Java
manifest и embedded Maven coordinates. Проекция ограничена 4000 символами;
усечение явно отмечается. SHA-256 относится к полному metadata-record, а не к
байтам библиотеки. Полный исходный каталог остаётся в evidence/image.syft.json.
Metadata остаются неподтверждёнными утверждениями пакета.

В evidence каждой записи включаются связанные наблюдения того же образа:
другие версии того же пакета и другие идентичности по точно тому же пути.
Они не исчезают на границе порций и имеют собственный ID, который можно
цитировать при оценке этой записи. До восьми связанных идентичностей и двух
наблюдений каждой; усечение обозначается явно. Исходники и неизвестные пути
не создают такие связи. Соседство в одном архиве не является автоматическим
основанием исключения: shading может объединять несколько настоящих пакетов.

[Сравнение до/после добавления контекста evidence](scoring-evidence-improvement.md):
два повтора на тех же трёх образах, без изменения порога.
