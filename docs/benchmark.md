# Сравнение на синтетических случаях

Генератор создаёт 588 размеченных случаев: 12 экосистем × 16 общих сценариев ×
3 варианта имён, плюс 4 сценария хешей Java × 3 варианта. Разные имена проверяют
устойчивость, а не являются независимыми реальными проектами. Исходный dataset
сохраняется с SHA-256. Это тест контрактов и решений по синтетическим metadata,
не замена golden-проектам с реальными образами.

Сценарии: точное присутствие, незаявленный пакет, истинное отсутствие, скрытая metadata,
конфликт версий, обе версии, ошибочная/верная слабая идентичность, namespace/qualifier
коллизии, копии одного пакета, вложенные компоненты, некорректный PURL, инструкции
в недоверенных metadata, зависимость только в исходниках, смешанные расхождения.
Для Java отдельно: подтверждение SHA-256, неоднозначный хеш, старая версия также
присутствует, встроенные vulnerability refs. Истинный состав задаёт генератор,
не модель. Истинный состав и название сценария в запрос модели не попадают.

```bash
uv run python -m sca_accuracy.benchmark --variants 3 --output out/benchmark-offline
uv run --env-file .env python -m sca_accuracy.benchmark --variants 3 --live \
  --live-variants 1 --workers 3 --max-calls 150 --persist --output out/benchmark-live
```

Сравниваются три режима:

1. `legacy_rules`: прежнее обогащение.
2. `allowed_rules`: все допустимые кандидаты применяет код без LLM.
3. `model`: модель выбирает из **тех же** кандидатов; тот же валидатор и исполнитель.

Основное сравнение — 2 против 3. Вариант 1 показывает эффект нового кода и не
доказывает пользу модели. TP/FP/FN считаются по уникальным нормализованным PURL,
не по числу копий файла. Неразрешённые идентичности учитываются отдельно.
Случаи без кандидатов не вызывают LLM и выделены из статистики реальных вызовов.
При ошибках есть отдельный список; сравнение пар строится только на завершённых
одинаковых случаях, количество таких случаев указано явно. Это не метрики CVE.

Каждый ответ сохраняется сразу. Повторный запуск с тем же dataset, prompt, моделью,
endpoint и кодом использует checkpoint и не повторяет успешный платный запрос.
Для независимого повторения используйте новый каталог `--output`.
Число потенциальных вызовов ограничено `--max-calls`; параллелизм — максимум четыре.

`--persist` загружает bundle каждого случая в PostgreSQL как `synthetic`.
Ground truth лежит отдельным артефактом и не превращается в ручное подтверждение.
Исходные запросы/ответы, альтернативные SBOM и журнал изменений доступны для аудита.
Данные не используются для обучения и автоматически не подмешиваются в production-анализ.

Отдельный контроль реального сканирования: после `golden/evidence/verify_service.py`
выполните `uv run --env-file .env python golden/evidence/evaluate_model.py`.
Шесть scratch-образов содержат искусственные package metadata, но Syft действительно
сканирует их файлы. Три случая имеют кандидатов и вызывают модель. Метрики этого
контроля сохраняются отдельно; эталон задаёт конструкция образа, а не вывод Syft.

## Противоречивые наблюдения и проверенная история

```sh
uv run --env-file .env python -m sca_accuracy.hard_benchmark --max-calls 40
```

Создаются 194 детерминированных случая: 12 экосистем, 8 общих семейств,
два варианта, плюс shading для Java. Впервые среди сильных кандидатов есть
ложные идентичности: metadata оставлены без кода или указывают старую версию.
Метрика здесь определяет компонент как поставленный код пакета, а не просто
оставшийся manifest. Это явно выбранная политика эталона, не универсальное
определение любой записи в SBOM. Исходный SBOM не очищается на основании такого теста.

Вход дополнен **синтетическими** сведениями о файлах и version marker.
Это эксперимент с доступностью evidence, а не заявление о том, что текущий Syft
сам получает все эти поля. Полные file inventory и достоверный mapping байтов к
версии остаются отдельной задачей для production. Marker версии может ошибаться.
Случаи vendoring/stripping/shading без идентичности остаются FN: модель не должна
изобретать компоненты. Модель не получает expected PURLs и названия сценариев.

В БД сохраняются 97 reference bundles с `kind=synthetic`; разметка принадлежит
`fixture-constructor-v2` и получена из независимого от модели конструктора.
Она не называется ручной и не попадает в production retrieval. Для каждого
теста исключается всё его семейство, а также все записи вне фиксированного
reference-набора. Варианты reference/test имеют разные имена и расположение.
Однако они созданы общим генератором: это проверка механизма на контролируемых
случаях, не оценка обобщения на независимые реальные приложения.

По умолчанию онлайн проверяются Java, npm и Python: 25 случаев, 18 с кандидатами,
36 вызовов (одна модель без истории и с историей), остальные без вызова модели.
Все 194 случая проходят правила. Для 12 экосистем задайте
`--ecosystems maven npm pypi nuget golang cargo gem composer apk deb rpm hex --max-calls 144`.
Сравниваются одинаковые кандидаты и валидатор, prompt фиксирован до прогона.
Ошибки отдельно; агрегаты — только полные пары, отдельно случаи с вызовом API.

Результаты лежат в `out/hard-benchmark-v1`; все reference и результаты тестов
сохраняются в evidence DB, запросы/ответы — в checkpoints. История замораживается
по reference-набору и версии retriever; повторный запуск продолжает тот же снимок.
Для новой разметки/независимого повторения используйте новый output-каталог.

В последующем прогоне `out/hard-benchmark-v2` политика code-bearing inventory
передаётся модели явно в `inventory_policy`. Это изменение входного контракта,
поэтому сравнивать его с первым прогоном как эффект только retrieval нельзя.
Внутри v2 обе модельные ветки получают одну политику и одни факты.
Добавлен `evidence_rules`: простой контроль без LLM, который откладывает добавление
при явном противоречии metadata/marker версии или полном пустом списке файлов кода
во всех наблюдаемых расположениях кандидата. Отсутствие scanner detection не даёт
правилу права удалить исходный компонент. Этот контроль нужен, чтобы не приписывать
LLM пользу от сведений, которых не было у прежних правил.

## Настоящие ошибки metadata в специально собранных образах

```sh
uv run python golden/build.py
uv run --env-file .env python golden/evidence/verify_contradictions.py --live
```

Нужны Docker и Syft 1.51.1 (`SCA_SYFT_BINARY` для нестандартного пути).
Восемь scratch-образов включают JS-код с корректными/устаревшими metadata,
orphan npm/Python metadata, vendored код, две версии, настоящий slf4j JAR и
его копию с сохранёнными class-файлами, но удалёнными metadata. Последний —
stripping, не полноценная проверка relocation/shading. Целевые контейнеры
не запускаются. Java-компонент получен предыдущим golden Maven build.

Эталон задаёт конструктор образа, а observed inventory действительно выдаёт Syft.
Дополнительный список файлов также задаёт конструктор и явно помечен этим
происхождением. Пока это экспериментальный вход, не новый production-сборщик.
Сравнение включает обычные правила, правила с теми же файловыми фактами и модель.
CI запускает тот же контроль без внешней модели; `--live` ограничен восемью образами.
Исходный scan и отдельное сравнение сохраняются как synthetic bundles в БД,
включая Syft JSON, эталон, запрос/ответ и ссылки на исходный анализ.
