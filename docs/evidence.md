# База evidence

PostgreSQL хранит неизменяемые результаты анализа, наблюдения, ссылки на файлы и
историю ручной разметки. Файлы хранятся отдельно, по SHA-256. API не использует
LLM-ответ как проверенную разметку и пока не подмешивает историю в запрос модели.

## Запуск

В `.env` задайте `SCA_POSTGRES_PASSWORD` (случайный URL-safe пароль), затем
`docker compose up --build -d`. PostgreSQL не публикует порт на хосте. Сервис
сохраняет evidence перед успешным завершением задания. Ошибка настроенной БД
завершает задание ошибкой; частичный результат не выдаётся за сохранённый.

Для CLI или внешней БД задайте `SCA_EVIDENCE_DSN` и `SCA_EVIDENCE_BLOBS`.
Без DSN анализ работает по прежнему, без записи в БД. Схема v1 создаётся автоматически
под PostgreSQL advisory lock; будущие несовместимые версии отвергаются.

```bash
uv run --env-file .env python -m sca_accuracy.evidence_cli out/golden
# Синтетические результаты помечаются отдельно:
uv run --env-file .env python -m sca_accuracy.evidence_cli out/example --kind synthetic
```

## Что хранится

- `evidence_runs`: тип `build`/`synthetic`, provenance, исходная оценка.
- `evidence_artifacts`: имя, точный хеш и размер сохранённого файла.
- `evidence_observations`: объявленный состав, каталог образа, выходной состав,
  отдельные оценки исходников; PURL и доступный SHA-256 для поиска.
- `evidence_labels`: подтверждение, опровержение или недостаточность данных с причиной
  и именем проверяющего. Новое мнение добавляется, старое не удаляется.

Одинаковый bundle повторно не добавляется. Поле generated_at у inventory/assessment
не влияет на идентификатор; изменившиеся наблюдения, provenance, модель, prompt или
код анализа дают новый результат. В `analysis-context.json` нет API-ключа.
Первый импорт сохраняет точные байты оригинальных JSON, включая timestamps.
Локальный CLI не знает commit; его provenance уже, чем у remote API.

Исходный SBOM, итоговый SBOM, coverage, Syft JSON и decisions хранятся как артефакты.
Связь утверждения с его источником восстанавливается через run, scope и исходный JSON.
При выдаче файла проверяется SHA-256. Неизвестные PURL сохраняются в исходных данных.

## API

Все endpoints требуют настроенного `SCA_API_TOKEN` и Bearer token:

- `GET /v2/evidence/runs?kind=build&purl=...&commit=...` — точный поиск; также доступны
  `sha256`, `image_id`, `repository`, `limit` (1–100), `offset`.
- `GET /v2/evidence/runs/{id}` — результат, наблюдения, артефакты и история разметки.
- `GET /v2/evidence/runs/{id}/artifacts/{name}` — исходные байты после проверки хеша.
- `POST /v2/evidence/runs/{id}/labels` — JSON с `observation_id`,
  `verdict` (`confirmed`/`refuted`/`insufficient`), `rationale`, `reviewer`.

Общий API token не удостоверяет имя человека: reviewer — заявленное имя.
Для корпоративной атрибуции нужен отдельный слой SSO/RBAC. Модель не пишет labels.
Необнаружение пакета не является автоматически подтверждённым отсутствием.

## Эксплуатация и проверки

Для локальных образов-fixture API v1 принимает `evidence_kind: synthetic`.
Это маркировка происхождения от вызывающего, не доказательство доверенности данных.
Проверка шести реальных scratch-образов с искусственными metadata через HTTP:
`uv run --env-file .env python golden/evidence/verify_service.py`.
Задайте `SCA_SERVICE_URL`, если сервис слушает не `http://127.0.0.1:18087`.
Целевые контейнеры не запускаются; проверяются каталог Syft, запись в БД и байты файлов.

Бэкапировать нужно согласованную пару: PostgreSQL и каталог evidence-blobs.
База не хранит образы целиком, только evidence; образ можно получить повторно по digest,
пока он есть в registry. После сбоя транзакции могут остаться непривязанные blobs;
автоматического удаления или политики retention пока нет. Не удаляйте тома для обновления.

Для тестов используйте отдельную БД и `SCA_TEST_EVIDENCE_DSN`. Тесты создают/удаляют
только свои случайные схемы. CI проверяет PostgreSQL, конкурентный повторный импорт,
целостность файлов, авторизацию, поиск, разметку и автоматическую запись из pipeline.
